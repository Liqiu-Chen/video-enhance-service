# 推理服务：VSR ×4 → RIFE ×2

把「先 4 倍视频超分、再 2 倍插帧」这条链路做成一个**可对外服务**的推理系统：
  
性能优化过的推理引擎 + 缓冲受控的串联流水线 + 网页/API 接口。

```
源视频 ──ffmpeg解码──▶ [入队缓冲] ──▶ VSR ×4 ──▶ RIFE ×2 ──▶ [出队缓冲] ──ffmpeg编码──▶ 成品
```

---

## 一、快速开始

```bash
PY=/c/Users/Administrator/.conda/envs/rife/python.exe
cd 推理服务

# 启动服务（默认监听 0.0.0.0:8000，局域网内其他机器可直接访问）
$PY serve.py
#   → 网页：http://<本机IP>:8000/
#   → 文档：http://<本机IP>:8000/docs
```

浏览器打开首页即可上传视频、看进度、下载结果。也可以直接调 API：

```bash
# 上传文件提交任务
curl -X POST http://127.0.0.1:8000/api/jobs \
     -F "file=@example.mp4" -F "interp=true" -F "realtime=true"

# 指定服务器本地路径（省掉上传）
curl -X POST http://127.0.0.1:8000/api/jobs/json \
     -H "Content-Type: application/json" \
     -d '{"path":"D:/project/FrameInterpolation/example_sr_and_FI.mp4"}'

# 查进度 / 下载 / 删除
curl http://127.0.0.1:8000/api/jobs/<id>
curl -o out.mp4 http://127.0.0.1:8000/api/jobs/<id>/result
curl -X DELETE http://127.0.0.1:8000/api/jobs/<id>
```

## 二、性能优化：哪些有效、哪些是坑

### 2.1 RIFE（2880×5120，批量 1）

| 配置                         | ms/对      | 加速          | 显存           | 与 fp32 的 PSNR  |
| -------------------------- | --------- | ----------- | ------------ | -------------- |
| torch fp32（原实现）            | 548.2     | 1.00×       | 5.95 GiB     | 基准             |
| torch fp16，warp 也是 fp16    | 276.8     | 1.98×       | 3.34 GiB     | **31.55 dB ✗** |
| **torch fp16 + fp32 warp** | **288.4** | **1.90×**   | 3.39 GiB     | **74.01 dB ✓** |
| 上面再加 CUDA Graph            | 296.5     | 1.85×       | **1.38 GiB** | 74.01 dB       |
| ONNX Runtime（fp16）         | 1646.2    | **0.33× ✗** | 0.83 GiB     | 40.01 dB ✗     |

**两个反直觉的结论：**

1. **fp16 不能无脑开。** RIFE 的 `warp` 走 `grid_sample`，坐标归一化到 [-1,1]。
     
   在 2880 宽的画面上相邻像素的坐标间距只有 `2/2879 ≈ 6.9e-4`，而 fp16 在 1.0
     
   附近的精度约 `1e-3` —— **坐标在 fp16 里根本区分不开相邻像素**，采样位置被量化，
     
   画面直接破坏。误差随分辨率增长：288p 55.6 dB → 1152p 41.0 dB → 2880p 31.6 dB。
     
   修法：只把这一步放回 fp32（`warplayer.FORCE_FP32_WARP`），卷积仍在 fp16 上跑，
     
   速度只掉 4%，PSNR 回到 74 dB。
2. **ONNX Runtime 在这条链上是负优化**（慢 3.3 倍）。BasicVSR++ 还要更糟：
     
   它依赖 `torchvision.ops.deform_conv2d`（可变形卷积），ONNX 里没有对应标准算子，
     
   根本导不出来。所以**本方案不做 ONNX**，走 PyTorch + fp16 + CUDA Graph。
3. **批量化在 5K 上没收益**：模型只有 3.04M 参数，算力早就饱和，batch 2 吞吐没变、
     
   显存翻倍，batch 4 直接爆显存落到共享内存（慢上百倍）。
4. **CUDA Graph 在这里是「省显存但不提速」，而且和 VSR 冲突。** 它能把 RIFE 的
     
   峰值显存从 6.78 压到 1.38 GiB，但**常驻**不释放；VSR 自己要 ~10 GiB，
     
   两者一叠加就把 16 GiB 顶满 → 溢出到共享内存 → GPU 100% 空转。
     
   实测开启后 32 帧跑了 5 分钟还没完（不开是 1 分 45 秒）。所以默认关闭。
5. **第一次跑会慢一大截，那是 cudnn 在选算法。** `torch.backends.cudnn.benchmark=True`
     
   会为每个新 shape 试探多种卷积算法，5K 尺寸下这一次性开销能到几十秒 ——
     
   最初实测「32 帧 VSR 段 82 s（2.6 s/帧）」其实稳态只有 ~0.8 s/帧。
     
   现在流水线在开跑前会先 `VsrEngine.warmup()` 把两种 shape 都过一遍。

### 2.2 VSR（BasicVSR++，720×1280 输入）

**先纠正一个前提：当前不是逐帧推理。** BasicVSR++ 每次吃一个 `(n, t, 3, h, w)`
  
的序列，`feat_extract` 本来就按 `n×t` 批量算；真正串行的是时间维的递归传播，
  
这是算法本身的性质，改不了。

#### ✅ 有效手段

| 手段                                  | 效果                                | 关键原因                  |
| ----------------------------------- | --------------------------------- | --------------------- |
| 干掉 PNG 往返 + `inference_mode` + fp16 | 1423 → 842 ms/帧（**1.69×**）        | 瓶颈是 PNG 编解码，不是模型      |
| **换 2x 输出模式**                       | 600.1 → **117.1** ms/帧（**5.12×**） | 输出像素少 4 倍，速度却快 5.12 倍 |

**2x 模式**：官方只有 ×4 权重，所以先对输入做 2x 下采样、再走 4x 超分，
  
最终输出正好是原图的 2 倍。用 `vsr_scale=2` 开启，下采样算法可选
  
`nearest / linear / area / bicubic`（默认 linear）。实测对比（720×1280 输入）：

| 模式        | ms/帧      | 显存           | 输出        |
| --------- | --------- | ------------ | --------- |
| 4x 直出     | 600.1     | 10.38 GiB    | 5120×2880 |
| **2x 模式** | **117.1** | **2.84 GiB** | 2560×1440 |

速度比像素减少倍数（4×）还快，说明 4x 模式额外受显存压力拖累。

#### ❌ 实测无效 / 不可用

| 方案                                       | 结果                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------- |
| **多段并行**（把多个段塞进 batch 维）                 | **负优化**：n=2 慢 12%、n=4 慢 24%，显存还翻倍（详见下表）                                          |
| Conv+BN 整网融合                             | **不适用**：模型 132 个 Conv2d、**BN 层 0 个**，没有可折叠的算子                                    |
| `torch.compile`                          | 不可用：需要 triton，Windows 官方无轮子                                                      |
| `torch.jit.script`                       | 失败：`Could not cast value of type NoneType to bool`                               |
| `torch.jit.trace` + freeze               | 失败：PyTorch 内部 assert（`stack_out->size() == 1`）                                   |
| `torch.ao.quantization.quantize_dynamic` | 实际替换了 **0 个层** —— PyTorch 动态量化只覆盖 Linear/LSTM，卷积网络不吃；而且它是 CPU 后端（fbgemm），GPU 上无效 |
| 剪枝（非结构化 30%）                             | 速度**完全没变**（112.5 → 112.7 ms/帧），质量**崩了**：PSNR 59.27 → **42.84 dB**                |
| CUDA Graph                               | 录制时 device-side assert，代码已删除                                                     |

**多段并行**（640×360 输入、段长固定 8，这是"多帧并行"唯一可行的实现方式）：

| n(段) | ms/帧         | 显存        |
| ---- | ------------ | --------- |
| 1    | **120.3**    | 2.80 GiB  |
| 2    | 134.8（慢 12%） | 5.58 GiB  |
| 4    | 148.9（慢 24%） | 11.14 GiB |

算力本来就饱和，合批只会多占显存、加剧缓存压力。**720×1280 输入下 n=2
  
需要的显存直接超过 16 GiB**（n=1 已占 10.38 GiB）。所以 `segments` 默认必须是 1。

**剪枝那条特别值得记住**：PyTorch 的剪枝是**掩码式**的，产生的是稀疏但不规则的
  
权重，稠密卷积核照样要算那些 0，所以不提速；而要恢复质量必须重新训练，
  
这里没有训练流程。**在这个场景下剪枝没有任何意义。**

#### 📐 段长与上下文帧（实测量化）

段长（overlap=2，720p 输入）：

| chunk | ms/帧      | 显存        | 备注                         |
| ----- | --------- | --------- | -------------------------- |
| 4     | 937.3     | 9.31 GiB  | 上下文只有 4 帧，时序建模更弱           |
| **8** | **832.8** | 11.58 GiB | 默认                         |
| 16    | —         | —         | **撑爆显存**（15.7/16.3 GiB 卡死） |

上下文帧 overlap（chunk=8，360p 输入）：

| overlap | ms/帧  | 相对    | 实际计算量 |
| ------- | ----- | ----- | ----- |
| 0       | 130.2 | 1.00× | 1.00  |
| 1       | 154.3 | 1.18× | 1.12  |
| 2       | 169.2 | 1.30× | 1.25  |
| 4       | 201.7 | 1.55× | 1.50  |

overlap 越小越快，代价是段边界失去时序上下文。默认 2 是折中；
  
赶时间可以调到 1 或 0 换约 12%~30% 的速度。

其余历史结论：`channels_last` 用不了（模型接口是 5 维 `(N,T,C,H,W)`，
  
`contiguous(memory_format=...)` 只接受 4 维）。

### 2.2b 4x 路径的深度剖析：为什么它快不了

上一轮优化完 2x 之后，针对**坚持 4x 输出**的场景又做了一轮剖析
  
（`profile_vsr.py` 算子级 + FLOP 估算 + 逐项实测）。

#### 先看结论：4x 是**算力受限**的，没有软件层的银弹

| 项目                  | 数值                                                                |
| ------------------- | ----------------------------------------------------------------- |
| 单次前向（10 帧）实测算力需求    | 约 **400 TFLOP**（`propagate` 的 4 个模块 × 每帧 15 个 64 通道 3×3 卷积占 ~95%） |
| 实测耗时                | ~8.5 s / 前向                                                       |
| → 实际有效算力            | **约 47 TFLOPS**                                                   |
| RTX 5070 Ti fp16 峰值 | 约 88 TFLOPS                                                       |

**已经在 ~53% 的效率上跑**。卷积本身没有明显浪费，所以纯软件手段最多再挤出个位数百分比。

#### ★ 真正的坑：cuDNN `benchmark=True` 的算法试探

| 场景                  | `benchmark=True`    | `benchmark=False` |
| ------------------- | ------------------- | ----------------- |
| 段长 8，第 1 轮（新进程）     | **1811.0 ms/帧**     | 897.3 ms/帧        |
| 段长 8，第 2 轮（算法缓存已建立） | 879.5 ms/帧          | 905.7 ms/帧        |
| 段长 4，预热 8 次后        | **>5 分钟跑不完 12 次调用** | 正常                |

`benchmark=True` 的稳态确实最快（880 ms/帧），但它会为每个新 shape 做算法试探，
  
实测这段**一次性开销 9~15 s**；而且**在段长 4 这种形状上会病态地慢**
  
（预热 8 次之后，12 次调用 5 分钟都跑不完）。

这正好解释了之前那个"32 帧 VSR 段报 82 s（2.6 s/帧）"的怪现象 —— 同一配置能测出
  
855 / 881 / 1811 三个完全不同的数。

**现在的做法**：默认 **`cudnn_benchmark=False`** —— 稳态只慢约 2%，但时间可预测、
  
不会在某个形状上突然崩掉。想榨那 2% 就传 `cudnn_benchmark=True`，
  
但务必先确认在你实际用的段长上不会病态变慢。

#### 两处已修掉的纯浪费（数值完全不变）

1. **`propagate` 里每帧白算 3 次 `zeros_like`**（`basicvsr_plusplus_net.py`）。
     
   `feat_n2 / flow_n2 / cond_n2` 写在 `if i > 1` 外面，i>1 的帧会先分配清零、
     
   紧接着被覆盖。t 帧就是 3(t+1) 次分配，实际只需要 3 次；单帧 118 MB，
     
   四个传播模块加起来是数 GB 的无效显存流量。已挪进 `else` 分支。
2. **SpyNet 正/反两个方向合成一次调用**。SpyNet 是逐对模型，两个方向互不影响，
     
   原来分两次调用纯属浪费：合批后卷积 batch 翻倍、kernel 启动次数减半。

改完用 16 帧片段跑通，产物目视确认画面正常、无伪影。

#### 又否掉的两个想法（都实测过）

| 尝试                     | 结果                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| `upsample` 的逐帧循环改成按帧合批 | **负优化 0.93×**（PSNR 完全一致）。该阶段占总量约 25%（30.4 ms/帧 @360p），但合批反而慢 8% —— 小 batch 下它的卷积已经够高效，合批只是增加显存压力 |
| 段长加大以摊薄 overlap        | chunk 16 在 5K 下**直接爆显存**（11.5 → 15.7 GiB 卡死）                                                     |

#### 测量方法上的坑（都会让你得出错误结论）

1. **`cudnn.benchmark=True` 必须预热足够次数再计时**，否则一次性试探漏进计时，
     
   同一配置能测出 855 / 1811 / 879 三个不同的数。
2. **引擎构造器会覆盖全局的 `torch.backends.cudnn.benchmark`** ——
     
   只在外层设 `torch.backends.cudnn` 再建引擎，参数会被引擎自己的默认值顶掉，
     
   导致"两种配置"其实测的是同一个（我踩过：测出 939 和 935，以为一样，
     
   其实是同一个配置测了两遍）。要测就必须 **传参给引擎**。
3. **基准素材绝不能用 `torch.zeros`**。全零输入会让 `check_if_mirror_extended`
     
   判定为镜像扩展序列，从而**跳过正向光流的计算**，耗时偏乐观。

### 2.2c ★ 流水线提速 3.5 倍：显存超限导致驱动换页

**症状**：流水线里 VSR 慢 4.8 倍（4476 vs 928 ms/帧），GPU 利用率 100%
  
但功耗只有 99W（满载应 250W+）—— 典型的"空转等显存"。

**决定性实验**（隔离环境，RIFE 只加载、不使用）：

| 配置              | VSR 速度                   | 显存预留          |
| --------------- | ------------------------ | ------------- |
| VSR 单独          | **928.7 ms/帧**           | 15.26 GiB     |
| VSR + RIFE 引擎共存 | **4476.4 ms/帧（慢 4.82×）** | **18.11 GiB** |

**光是"把 RIFE 引擎建出来放着不用"，VSR 就慢 4.8 倍。**

原因：两者合计预留 **18.11 GiB，而 5070 Ti 只有 16.3 GiB** → 超出物理显存 →
  
驱动层换页 → 计算空转。

> ⚠️ **关键认知：看显存够不够必须看 `memory_reserved()`，不是 `memory_allocated()`。**
>   
> VSR 4x 的已分配峰值只有 9.31 GiB，但 **reserved 高达 15.26 GiB**（94%）——
>   
> 缓存分配器会留住大块空闲块。我一开始就是按 allocated 判断的，才判断失误。
>
> 而且 VSR 单跑在 94% 占用下**本身就不稳**：同一配置两次跑出 928 和 3956 ms/帧。
>   
> 这一整轮所有自相矛盾的测量（0.84/1.7/2.1/2.75/4.5 s/帧）根子都在这里。

**修法（已验证）**：每次调用后把缓存池还给驱动。

| 策略                                   | VSR 速度              | 显存预留         |
| ------------------------------------ | ------------------- | ------------ |
| 不释放                                  | 932.5 ms/帧          | 15.26 GiB    |
| **每次调用后 `torch.cuda.empty_cache()`** | 968.5 ms/帧（仅慢 3.9%） | **0.04 GiB** |

已接进 `pipeline.py`：每个微批跑完 VSR 后、RIFE 跑完后各释放一次。

**效果（16 帧 4x 片段，chunk4）**：

|       | 修复前     | **修复后**          |
| ----- | ------- | ---------------- |
| 主循环   | 77.8 s  | **36.2 s（2.1×）** |
| VSR 段 | 72.6 s  | **30.4 s（2.4×）** |
| 总耗时   | 212.3 s | **61.1 s（3.5×）** |

**顺带修掉的三处**：

1. **`RifeEngine.build()` 的提前返回条件写错**：`and (self.graph or self.session)`，
     
   而 torch 后端两者恒为 None → **每个微批都重建后端并白跑 2 次全尺寸预热前向**。
     
   改用显式 `_built` 标志。
2. **预热输入不能用 `np.zeros`**：全零序列被 `check_if_mirror_extended` 判成
     
   "镜像扩展"，**跳过正向光流计算** → 那条分支的 kernel 从没初始化，
     
   拖到第一个真实微批才首次加载（那一批要 17 s）。改用非零随机图后，
     
   预热从 207 s 降到 **22 s**。
3. **`rife_batch` 默认 2 → 1**（实测 b1 更快且显存减半）。

**试过但无效**：`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（预留不变、
  
速度不变）；段长降到 2（预留 16.50 仍贴边，且 overlap 变 2× 计算 → 更慢 5940 ms/帧）。


### 2.2e ★★★ 按真实需求尺寸重新调优（720x1280 → 1440x2560）

**之前的基准都建立在 `720p → 2880x5120` 上，那是错的靶子** —— 2880x5120 已经超过
2K，视频流里基本用不到。真实需求是 **480p→1080p** 这一档，对应本项目就是：

```
720x1280  ──先降2倍──▶  360x640  ──4x超分──▶  1440x2560
```

**尺寸小了 4 倍，之前所有结论都反转了**（720x1280 输入、8 帧）：

| 后端 | 配置 | ms/帧 | 峰值显存 |
| --- | --- | --- | --- |
| **BasicVSR++** | **chunk=8** | **172.3** ⭐ | **3.09 GiB** |
| BasicVSR++ | chunk=4 | 198.2 | 2.52 GiB |
| BasicVSR++ | chunk=16 | 310.2 | 5.02 GiB |
| BasicVSR++ | chunk=32 | 582.9 | 7.75 GiB |
| Real-ESRGAN | batch=1 | 221.9 | 1.05 GiB |
| Real-ESRGAN | batch=4 | 246.3 | 4.10 GiB |

**反转 1：VSR 反超单帧 SR**（172.3 vs 221.9 ms/帧）。之前在 2880x5120 下 VSR 慢，
是因为显存 15.26 GiB 触发驱动换页；这个尺寸下只要 **3.09 GiB**，换页消失。
而且 VSR 还带时序一致性（视频质量更好）。
→ **目标尺寸下 `sr_backend="vsr"`, `vsr_chunk=8` 才是最优，不是 Real-ESRGAN。**

**反转 2：chunk=8 成了最优**（之前在 4x 输出下只能用 chunk=4，再大就爆显存）。

**合批依旧无收益**（batch=1 最好，batch=4 反而慢 11%）—— 再次印证这类模型
在这个尺寸上也是**算力饱和**的。

**分块与 2x 模式互斥**（代码里已断言）：分块在**原图**上切，而 2x 模式是在块内
再降采样，坐标网格错位。

#### 端到端（128 帧 720x1280 → 1440x2560）

| | VSR chunk=8 | RealESRGAN batch=1 |
| --- | --- | --- |
| 预热 | 8.4 s | 0.5 s |
| SR 段 | **23.4 s（183 ms/帧）** | 28.8 s（225 ms/帧） |
| RIFE 段 | 10.4 s（81 ms/帧） | 9.5 s（74 ms/帧） |
| **总耗时** | 43.7 s | **40.4 s** |

VSR 每帧省 42 ms 但要多付 7.9 s 预热 → **盈亏平衡点约 190 帧**。
791 帧的成片 VSR 会赢（服务在启动时预热，更是稳赢）。

**吞吐**：约 **3 源帧/秒** → 791 帧整片约 **4.2 分钟**
（对比原 4x 链路 42 分钟，**快约 10 倍**，而且输出分辨率才是真实需要的）。

#### 随尺寸改的两个设置

1. **`empty_cache()` 改为按需触发**：预留量 > `cache_flush_gb`（默认 8 GiB）才释放。
   目标尺寸下 VSR 只占 3 GiB，不会触发，省下之前白白付出的 ~4% 开销；
   只有回到 2880x5120 那种高占用场景才会自动启用。
2. **服务默认值切到目标场景**：`sr_backend="vsr"`、`vsr_chunk=8`、`vsr_scale=2`、
   `resr_batch=1`。

> ⚠️ **教训：性能结论必须绑定分辨率。** 同一份代码在 2880x5120 和 1440x2560 上
> 最优配置完全相反（后端选择、段长、是否分块全都翻过来）。
> 以后调优先问"目标分辨率是多少"。


## 二·补、自动配置（autoconfig.py）

**为什么需要**：性能结论强烈依赖分辨率，手工调参很容易踩到
"显存超限 → 驱动换页 → 性能崩 4 倍（而且不报错，只是慢）"这个坑。
实测同一份代码在两个尺寸上最优配置完全相反：

| 输出尺寸 | 最优后端 | 显存 |
| --- | --- | --- |
| 1440x2560（3.7 MP） | **BasicVSR++ chunk=8**（172 ms/帧） | 3.09 GiB |
| 2880x5120（14.7 MP） | VSR 要 **15.26 GiB** → 换页；必须 Real-ESRGAN | 0.06 GiB |

**做法**：按输出像素分档给一条**候选链**，逐个试跑预热并核对
`max_memory_allocated` 是否在预算（默认 12 GiB）内，超了就降级换下一个。

```
2x 档（≤4 MP）： VSR chunk8 → VSR chunk4 → RealESRGAN batch2 → batch1
中档（≤9 MP）：  VSR chunk4 → RealESRGAN batch1 → +tile512
大档（>9 MP）：  RealESRGAN batch1 → +tile512 → +tile256     （VSR 直接排除）
```

静态估算只用来排序，**准入以实测峰值为准** —— 桌面程序也会占显存，估算不准。

服务里默认开启；显式传 `sr_backend` 可跳过自动选择。

实际日志：
```
[auto] 输入 720x1280 → 输出 1440x2560（3.7 MP，小尺寸档）
[auto] 选用 vsr {'chunk': 8, 'tile': 0}  实测峰值 3.10 GiB (预算 12)
微批#1..#16 VSR 8帧 -> 1.40~1.52s (174~190 ms/帧)   ← 16 批全稳定，无抖动
```


## 二·补·3、TensorRT 优化（RIFE 可用 / VSR 不通）

先回答「流水线还是隔离」：**同素材同参数下两者只差 5%，保持流水线。**

| 跑法 | ms/帧 | 总耗时 |
| --- | --- | --- |
| 隔离（VSR 全跑完再 RIFE） | 100.9 | 24.2 s |
| **流水线（交替微批）** | 106.1 | 25.5 s |

> ⚠️ 第一版脚本拿 240 帧对比**整个 1158 帧素材**（`pipe.run` 会跑完整个文件），
> 算出"流水线慢 4.88 倍"的假象。**比性能必须统一帧数。**

干扰源排查结论：**线程与 ffmpeg 进程完全不影响 GPU 吞吐**
（后台编码 0.98x、空转线程 0.97x、解码线程 0.97x）。

### VSR（BasicVSR++）：无法走 TensorRT（已实证）

`SecondOrderDeformableAlignment` 用 `torchvision.ops.deform_conv2d(mask=...)`
——**带掩码可变形卷积**。ONNX 到 opset 28 也只有无 mask 的 `DeformConv`，
PyTorch 导出器也没为它注册 symbolic，实测报
`UnsupportedOperatorError: unrecognized namespace {op_name}`。
TensorRT 同样没有原生 DeformConv，要自行编译 plugin。
结论落盘在 `cache/trt_vsr_feasibility.json`，见 `build_trt_vsr.py`。

### RIFE：容器可用，已设为服务默认

960x1696、真实视频帧：

| 实现 | ms/对 | 精度（vs torch-fp32） |
| --- | --- | --- |
| PyTorch fp16+warp32（原配置） | 26.4 | 76.73 dB |
| TensorRT fp32 | 30.2 | **107.63 dB** |
| **TensorRT fp16（采用）** | **10.7（2.47x）** | **61.15 dB** |

端到端（240 帧）：RIFE 段 **29.6 → 13.3 ms/帧（2.2x）**，
总耗时 105.8 → **89.3 ms/帧（1.19x）**，RIFE 显存 0.39 → 0.12 GiB。
liuqiang 全片 **124.6 → 105.1 s**，成品逐帧比对 **PSNR 平均 44 dB**（等价）。

引擎构建约 20 s，缓存在 `cache/rife_<h>x<w>_<mode>.trt`。
服务默认 `rife_backend="trt"`，环境没有 TensorRT 时**自动退回 torch**。

### ★ 两个隐蔽的坑

1. **TRT 的输入 dtype 必须读**（不能只读输出）。ONNX 是 fp32 导出的、
   引擎输入期待 fp32，而喂的是 fp16 张量 → 引擎按 fp32 解引用 fp16 缓冲区
   → 读到**未初始化内存**，表现为 PSNR 5.5 dB、最大差 545（输出值域才 0~1）。
   看起来像"精度崩了"，其实是绑错了内存。
2. **测精度绝不能用随机噪声**。噪声下**连 PyTorch 自己的 fp16 都只有 21 dB**
   ——噪声是最病态的输入，任何数值差异都被放大。换成真实视频帧后
   torch-fp16 76.7 dB、TRT-fp16 61.2 dB，一切正常。

## 二·补·2、网页端 2x 能力

网页"输出倍率"下拉框可选 **×2（推荐）** / ×4，对应 `vsr_scale` 参数。

2x 的实现就是「**输入先 2 倍下采样 → 再走 4x 超分**」（官方只有 x4 权重）。

> **下采样开销实测：0.02 ms/帧，占 2x 模式单帧（222 ms）的 0.01% —— 已经是免费的。**
> 三组测量（不做降采样 / 当前实现 / 优化版）都是 0.15 ms，完全在噪声里。
> 所以这里**没有做"性能优化"**，因为不存在可优化的部分；只把默认算法从
> `bilinear` 换成 `avg_pool2d`（真正的 2x2 箱式平均，抗锯齿更好）——**零成本换质量**。

### 2.3 端到端（32 帧片段，720×1280 → 2880×5120）

| 阶段      | 旧         | 新        | 加速    |
| ------- | --------- | -------- | ----- |
| VSR ×4  | 1423 ms/帧 | 842 ms/帧 | 1.69× |
| RIFE ×2 | 1070 ms/帧 | 294 ms/帧 | 3.64× |

**服务端跑真实任务的实测**（`POST /api/jobs/json`，32 帧片段，`crf=18`）：

```
status: done   frames 32 -> 64   2880x5120 @120fps   0.533s   7.8 MB
stages: vsr 51.4s   total 95.7s
```

两点说明：

- `total` 里含**首次调用的预热**（cudnn 算法选型），服务常驻时每个分辨率只付一次。
- VSR 每帧耗时的测量本身**波动较大**（同一份代码测到过 0.84 / 2.1 / 1.7 s/帧），
    
  差异主要来自 cudnn 选型是否已经热完、以及是否和别的进程抢 GPU。
    
  上表的 842 ms 是"已热"读数；保守按 1.6 s/帧估计更稳。
- 流式微批会在**批边界重启 VSR 的时序传播**，总处理帧数也比单次调用多约 25%
    
  （重叠帧重复计算）。这是「内存有上限」换来的代价，符合预期。

## 三、缓冲管理

原方案有两个会直接崩掉的问题，这里都从结构上解决：

1. **中间结果不落盘。** 两级模型之间用**有界队列**直传，不再写 PNG 再读回来。
2. **每个队列都有上限**（`queue_in=6` / `queue_out=24` 帧）。拉满就阻塞上游 ——
     
   内存占用有硬上限，不会因为上下游速度不匹配而无限堆积。
     
   旧实现在内存里攒 791 帧（单帧 2880×5120×3 float32 = 169 MB，合计 134 GB），
     
   跑到第 300 帧就 `numpy._ArrayMemoryError`。
3. **微批处理**：源帧切成 `micro_batch` 大小的块依次过两级模型，峰值内存与视频总长无关。
4. **帧只以 uint8 存在**：5K 单帧 42 MB 而不是 169 MB，内存/显存压力都降到 1/4，
     
   而 8bit 素材本来就只有 256 级。
5. **三线程重叠**：解码（ffmpeg）/ 推理（GPU）/ 编码（ffmpeg）分别在独立线程，
     
   总时间趋向 `max(IO, GPU)` 而不是相加。

服务侧另外还有一层：每个任务一个独立工作区、受理前检查磁盘余量、
  
成品按 TTL（6 小时）自动清理、队列上限 16。

## 五、为什么是「单 worker + 排队」

本机只有一块 16 GiB 的 GPU，而 VSR ×4 在 5K 下光激活就要 ~10 GiB。
  
并发跑两个任务只会互相抢显存然后双双 OOM —— 所以用队列把并发度压到 1，
  
多用户靠排队而不是靠并行来支撑。任务状态里有 `queue_wait_s` 可以看到排了多久。

## 七、让局域网外的用户访问

本机在**中国移动家庭宽带**后面：内网 IP `192.168.5.17`，出口公网 IP
  
`117.185.177.41`。这种环境**不能靠端口映射**（运营商大内网 + 入站端口封锁），
  
必须走内网穿透。

### 7.1 当前方案：SSH 反向隧道（免注册、免下载客户端）

用 `public.py` 一步搞定，它会自动重连并把**当前**地址打印出来：

```bash
$PY public.py
# → 公网访问地址： https://xxxxxxxx.lhr.life/?token=<令牌>
```

等价的手工命令：

```bash
ssh -T -o StrictHostKeyChecking=no -o ServerAliveInterval=20 \
    -o ExitOnForwardFailure=yes -R 80:localhost:8000 nokey@localhost.run
```

> ⚠️ **免费隧道的地址是临时的。** 实测 SSH 一断线重连就换域名
>   
> （第一次拿到 `1a5b082e392309.lhr.life`，重连后变成 `0e41e88c4484f5.lhr.life`，
>   
> 旧地址立刻 502）。所以**每次重连后都要把新地址重新发给对方**。
>   
> 想要固定域名需要注册账号并挂上自己的 SSH 公钥
>   
> （见 <https://localhost.run/docs/forever-free/>）。
>
> ⚠️ **下行速度实测只有 ~20 KB/s**（走国际线路）。网页和短片段没问题，
>   
> 但 550 MB 的 5K 成品根本传不动（要 7 小时以上）。

1. **自建最靠谱**：一台有公网 IP 的云服务器跑 frp 或 SSH 反向隧道，
     
   带宽自己说了算，地址也稳定。
2. 或者用国内穿透服务（natapp / 花生壳）的付费版，走国内线路，速度比国际隧道好得多。
3. 找运营商申请公网 IP —— 家庭宽带一般不给。
4. **成品太大就传不出去**：给对方用时建议先降分辨率或只切片段，
     
   5K@120fps 的 12 秒片段就有 550 MB。

### 7.4 对外提供前请想清楚

- **这是你的家用机器**：对方提交 5K 视频，一张 5070 Ti 跑 791 帧要 **40 分钟以上**，
    
  而且同一时刻只能跑一个任务（其余排队）。
- **上传上限 512 MB**，超大文件请先压缩或切片段。
- **带宽是硬瓶颈**：家庭宽带上行通常只有几十 Mbps，对方下载会很慢。
- 令牌泄露 = 别人可以随便用你的 GPU。**不要在公开群里直接发带令牌的链接。**
- 服务只适合内网/可信用户，没有用户体系、没有限流、没有审计。

### 7.5 ★★★ 固定域名的正确做法（关键）

**注册账号 + 挂密钥之后域名还是每次都变？** 因为**用户名用了 `nokey`**。

FAQ 原文：

> Free tunnels change domain names after a few hours. To keep your domain name
> between connections make sure you have an SSH key **and that you are not using
> the `nokey` username**.

`nokey` 是"**跳过密钥校验、走匿名通道**"的专用账号 —— 用了它，密钥永远不生效
（`ssh -v` 里会显示 `Authenticated ... using "none"`，就是没在用密钥的信号）。

**正确命令**（注意**去掉 `nokey@`**）：

```bash
ssh -i work/tunnel_key -o ServerAliveInterval=10 \
    -o ExitOnForwardFailure=yes -R 80:localhost:8000 localhost.run
```

实测**两次独立连接拿到完全相同的子域** → 域名已固定，断线重连不再变。
`public.py` 已按此实现：**有密钥就用普通用户名，没密钥才退回 `nokey@` 匿名**。

其他须知（FAQ 原文）：

- 免费域名**几小时后**仍会变一次（防钓鱼站）；要永久稳定需**付费 Custom Domain 计划**。
- 免费通道**有限速**：实测上传 ~10 KB/s、下载 ~20 KB/s。
- 建议加 `-o ServerAliveInterval=60` 防空闲超时；要自愈就把 ssh 包在循环里。

## 八、已知限制

- **只有一块 GPU**：同一时刻只跑一个任务，人多时排队。
- **上传上限 512 MB**：再大请用 `path` 走服务器本地路径。
- **仅支持 ×4 超分 + ×2 插帧**：VSR 的官方权重只有 scale=4 一档。
- **VSR 的 `max_seq_len` 受显存限制**：分段越小越省显存但时序建模越弱
    
  （当前默认 8，原先为了显存只能用 4）。
- 页面是单文件静态页，没有鉴权 —— **只适合内网**，别直接暴露到公网。
